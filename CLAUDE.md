# Learning Companion

A learning companion for tracking goals and learning sessions, attaching resources, and getting AI-powered summaries and next steps. Built with Django through an AI-factory pipeline (Recap Project 6, handouts in `instructions/`).

## Stack

- Python 3.14, Django 6.1, SQLite (dev, tests and container)
- Server-rendered Django templates, Tailwind via `django-tailwind-cli` (standalone binary, no Node). The Tailwind version is pinned in `settings.py` (`TAILWIND_CLI_VERSION`), and the built CSS is git-ignored, so run `tailwind build` after checkout. Tests don't need the build.
- UI: daisyUI 5.7.47 through its standalone setup with the official Tailwind binary. `TAILWIND_CLI_SRC_CSS = "tailwind/source.css"` (relative to `src/`, kept out of `STATICFILES_DIRS` so `collectstatic` doesn't publish it) loads the committed `src/tailwind/daisyui.mjs` and `daisyui-theme.mjs`; its header records the version and each file's sha256, which `core/tests/test_theme.py` checks, and `@source not "./daisyui{,*}.mjs"` keeps the build from scanning them. To update daisyUI, download both files from the release, then update the version and the hashes. `themes: false` drops the built-in themes; the two custom ones are `companion` (light, `default: true`) and `companion-dark` (`prefersdark: true`, so it follows the OS), indigo/violet `primary` on slate. The header's theme switch (`base.html`, one `components/_theme_option.html` per choice) is CSS-only, through daisyUI's `theme-controller`: a `<fieldset>` (legend "Theme") of three `name="theme"` radios, System (`value="system"`, checked, matches no theme, so the OS decides), Light (`companion`) and Dark (`companion-dark`). daisyUI's `:root:has(input.theme-controller[value=…]:checked)` selector outranks the `prefersdark` rule, so a pick beats the OS. It isn't remembered: every page load starts at System (the user's choice over a cookie or JavaScript). It sits in the header, outside every `nav`, `main` and `form`, so tests that collect a form's fields scope them to `<main>`. Sidebar menu items get a primary `:focus-visible` outline in `source.css`, and daisyUI's faded text (table `thead`/`tfoot`, inactive tabs) takes `text-base-content` to keep 4.5:1. Every colour is an sRGB-gamut `oklch()` and every `*-content` colour has at least 4.5:1 contrast on its background (and `base-content` on `base-100/200/300`); the test computes both, so a colour change that breaks either is red. The build only finds class names written out in templates or `.py` files: never build one (`alert-{{ tag }}`), branch on literal ones instead (as `base.html`'s messages, `components/_status_badge.html` and `core.forms.WIDGET_CLASSES` do). The site needs no JavaScript.

The toggle is the checkbox `#nav-drawer` (`aria-label="Menu"`, no `name`, `md:hidden`); the header's `label.drawer-button` and the overlay label are only pointer targets. `.drawer-side` comes before `.drawer-content` in the markup (the grid places both), so an opened drawer's links are next in the Tab order (tested). The one `<nav aria-label="Main">` sits in `.drawer-side` and is rendered once: `accounts/tests/test_nav.py` pins its links and text exactly (no icons with text, no extra links; the brand link to `/` is in the header, which links nowhere else) and the log-out POST form inside it. The current section's link has `aria-current="page"` and `menu-active`, from `request.resolver_match.namespace` (no query; sessions and resources count as Goals). Messages are daisyUI alerts per level: `role="alert"` for errors, `role="status"` otherwise. Every page sets `{% block title %}<Page> · Learning Companion{% endblock %}` (home keeps the bare name) and has one `<h1>` with no skipped heading levels.

No `django/forms/*` template is overridden, so the admin renders exactly as before (tested). `field.html` keeps Django's `<id>_helptext` and `<id>_error` ids, which Django's own `aria-describedby` and `aria-invalid` point to; non-field errors are a `role="alert"` alert.

- Auth: Django's built-in auth with the custom user model `accounts.User` (`AUTH_USER_MODEL = "accounts.User"`, an `AbstractUser` with no extra fields). Always refer to it through `get_user_model()` or `settings.AUTH_USER_MODEL`, never `django.contrib.auth.models.User`. Profile data goes on `profiles.Profile`, not on `User`. Every user saved through `save()` gets exactly one profile (`user.profile`: `name`, `cohort`, `focus_areas`). A `post_save` signal in `profiles/signals.py` creates it, and the data migration `profiles/0002` backfilled users who already existed. `bulk_create` and raw fixture loads skip the signal, so views must use `Profile.objects.get_or_create(user=request.user)`, not a bare `user.profile`. The User admin (`accounts/admin.py`) shows it as an inline on the change page only, never on the add page. Users view and edit their own profile at login-required pages: `/profile/` (`profiles:mine`) redirects to `/profile/<pk>/` (`profiles:detail`), and `/profile/<pk>/edit/` (`profiles:edit`) takes focus areas as comma-separated text. Any view that takes a pk must scope its queryset to `request.user`, as `profiles.views.OwnProfileMixin` does for profiles, so another user's pk is a 404, exactly like a missing one. A profile takes at most 20 focus areas (1,000 characters of input), checked before any tag lookup. Sign-up (`/accounts/signup/`), log-in (`/accounts/login/`) and log-out (`/accounts/logout/`, POST only) are `accounts` views, the last two thin subclasses of Django's `LoginView` and `LogoutView`. `LOGIN_URL = "accounts:login"`, `LOGIN_REDIRECT_URL = "dashboard:index"` (URL names, resolved: log-in, sign-up and an already logged-in visit to either land on the dashboard) and `LOGOUT_REDIRECT_URL = "/"` (log-out must land on a public page; `/` is the same home page for everyone). Auth tests assert the literal `/dashboard/`, not the setting. A `next` parameter is followed only for same-site URLs (Django's `url_has_allowed_host_and_scheme`); keep it that way for any new redirect.
- Tags: one shared `tags.Tag` vocabulary, used for a profile's `focus_areas` and for a learning session's `tags`. Names are normalised (NFKC, trimmed, inner whitespace collapsed), must not contain control or invisible characters (Unicode Cc/Cf) or commas (the separator for typed tag lists), and are unique regardless of case, through a database constraint on `Lower("name")`; on SQLite the case folding is ASCII-only. `Tag.objects.clean_name()` validates a name without touching the database (forms use it to reject bad entries before anything is saved). `save()` normalises the name; the 50-character limit and the character checks apply only through `full_clean()`/`clean_name()`; `update()` and `bulk_create()` bypass all of it. Rows written before the normalisation existed (or through those bypasses) aren't renormalised: there is no data migration, as there is no production data yet. So always turn typed input into tags with `Tag.objects.get_or_create_by_name()`, never `Tag.objects.create()`. It is the only creation path for typed names: it validates before its lookup (an over-long name is a `ValidationError`, never a database error), and it is safe when two requests create the same name at once. Forms take typed tags through `tags.forms.TagListField` (comma-separated text, so a form never lists other users' tags): it cleans to a list of names, NFKC-splits on commas, validates each entry with `clean_name()` (every bad entry named in the error), drops case-insensitive duplicates (the first spelling wins) and caps the input at 20 names and 1,000 characters (`max_tags`, and `noun` for the count message). It creates nothing; the form's `@transaction.atomic save()` and `_save_m2m()` turn the names into tags with `get_or_create_by_name()`, so a failure leaves neither the object nor new tags. `tags_as_text()` builds the field's initial value. `ProfileForm` (`noun="focus areas"`) and `LearningSessionForm` use it.
- Goals: `goals.Goal` is owned by one user (`owner`, `user.goals`, deleted with the user). Its fields are `title` (required, up to 200 characters, stored trimmed), optional `description`, `status` and `created_at`/`updated_at`. `Goal.Status` is a `TextChoices` with `planned`, `in-progress` and `done` (the hyphen matches the planned `?status=` filter); a database `CheckConstraint` enforces them, so `update()`/`bulk_create()` can't store anything else. Goals are ordered newest first (`-created_at`, then `-id`). Django leaves `Meta.ordering` out of `values().annotate()` GROUP BY queries, but an explicit `order_by(...)` on the queryset adds its columns and splits the groups, so a grouping helper clears it with `.order_by()`. `GoalQuerySet.status_counts()` does that: it returns `{status: count}` for every `Goal.Status` value in choice order (0 when none) in one grouped query, also on an ordered queryset (pinned by a test); chain it after `owned_by(user)`. Logged-in users list their goals at `/goals/` (`goals:list`, 20 per page) and create them at `/goals/new/` (`goals:create`). Each goal has a detail page `/goals/<pk>/` (`goals:detail`, which `Goal.get_absolute_url()` returns), an edit page `/goals/<pk>/edit/` and a delete confirmation `/goals/<pk>/delete/` (POST deletes). The detail page has a Sessions section (`aria-labelledby="sessions-heading"`; Summary, Next steps, Sessions and Resources are all labelled daisyUI cards): the 5 most recent sessions, the total time of all of them (one `Sum()` aggregate) and links to add a session and to the full list; the delete confirmation says how many sessions (and resources) are deleted with the goal. Both look sessions up through `LearningSession.objects.owned_by(request.user).filter(goal=...)`, and the detail page keeps a fixed query count (pinned by `assertNumQueries`; the Resources section adds one query, see Resources). Create and edit redirect to the goal through `get_absolute_url`. Every goal view looks goals up through `Goal.objects.owned_by(user)` via `goals.views.OwnGoalsMixin`, so another user's goal is a 404 identical to a missing one. **List `OwnGoalsMixin` first in a view's bases and never set `model` on a goal view**: listed later, Django's own `get_queryset()` wins, which raises `ImproperlyConfigured` without a model but would serve every user's goals with one. `GoalViewsScopingTests` walks `goals.urls` and enforces both rules for every goal lookup view (a new route must be added to it deliberately). The list filters by `?status=<planned|in-progress|done>` (unknown values show all); its pagination links use Django's `{% querystring %}` tag, so they keep the filter and escape anything else in the query. `GoalForm` has an explicit field allow-list (never `owner`); the owner is set from `request.user` in `form_valid`. The description is capped at 2,000 characters by a model-level `MaxLengthValidator`, so forms, `full_clean()` and the admin share one limit. A goal stores its latest AI progress summary in `summary` (blank until generated) and `summary_generated_at`; neither is in `GoalForm`. `goals:summary` (`/goals/<pk>/summary/`, `GoalSummaryView(OwnGoalsMixin, SingleObjectMixin, View)`, POST only, so anything else is a 405) generates it: through `owned_by` it gathers the 10 newest sessions (`with_tags()`), the total over all sessions and the 20 newest resources (`goals.views.prompt_data()`, with `PROMPT_SESSIONS` and `PROMPT_RESOURCES`, shared with next steps), builds the messages with `goals.prompts.summary_messages()` (a pure function; the user message comes from `goal_message()`: goal title, status, description, one line per session and per resource, missing parts named), calls `ai.services.complete(..., max_retries=0)` and saves with `update_fields=["summary", "summary_generated_at"]`, so `updated_at` doesn't move. A goal with no sessions and no resources isn't sent ("Log a session or attach a resource first."), and an `AIServiceError` is always caught and shown as a message, never a 500; every outcome redirects to the goal page. The detail page's Summary section (`aria-labelledby="summary-heading"`) shows the summary (`linebreaksbr`, escaped) and its time, or "No summary yet.", and a POST form whose button reads "Generate summary" or "Regenerate summary"; the summary comes with the goal row, so the detail page's query count stays at 7. Summary view tests extend `goals/tests/test_views.py`'s `SummaryTestCase`, which mocks `ai.services.complete` and fails any real OpenAI client construction. A goal also stores its latest 2-3 AI next learning steps in `next_steps` (a `JSONField`, a list of strings in order, `[]` until suggested) and `next_steps_generated_at`; neither is in `GoalForm`. `goals:next_steps` (`/goals/<pk>/next-steps/`, `GoalNextStepsView(OwnGoalsMixin, SingleObjectMixin, View)`, POST only) sends the same data as the summary through `prompt_data()` with `goals.prompts.next_steps_messages()` (the same user message; the system prompt asks for 2 to 3 concrete, actionable steps that build on what has been done without repeating attached resources, "how to start" for a goal without sessions, as a JSON object with a `steps` list), calls `ai.services.complete_json(..., name="next_steps", schema=NEXT_STEPS_SCHEMA, max_retries=0)`, turns the reply into steps with `parse_next_steps()` (trimmed, blank ones dropped; anything but 2-3 strings is the unexpected-reply `AIServiceError`) and saves with `update_fields=["next_steps", "next_steps_generated_at"]`. Unlike the summary, a goal with no sessions and no resources is still sent (the user's choice: that's when "how to start" helps most). Every `AIServiceError` is caught and shown, the earlier steps are kept, and every outcome redirects to the goal page ("Next steps suggested." on success). The detail page's Next steps section (`aria-labelledby="next-steps-heading"`, right after Summary) shows the steps as an `<ol>` (escaped) with "Suggested <time>", or "No next steps yet.", and a POST form whose button reads "Suggest next steps" or "Suggest new next steps"; the steps come with the goal row, so the query count stays at 7. Next-steps view tests extend `NextStepsTestCase`, which mocks `ai.services.complete_json` and fails any real OpenAI client construction.
- Learning sessions: `learning_sessions.LearningSession` (app `learning_sessions`, because the label `sessions` belongs to `django.contrib.sessions`) records time spent on one goal. `goal` is a required foreign key (`goal.sessions`, deleted with the goal and so with its user). `date` defaults to today (`timezone.localdate`), and the `reject_future_dates` validator rejects a future date. That runs only through `full_clean()`, with no database constraint because "today" moves. The initial migration refers to the validator by its dotted path, so renaming it needs a migration. `duration_minutes` is whole minutes, 1 to 1,440, enforced by validators and by a `CheckConstraint` (`PositiveIntegerField` alone would allow 0); hour totals divide `Sum()` by 60. `notes` is optional and capped at 2,000 characters by a `MaxLengthValidator`, and `tags` is a many-to-many to `tags.Tag` (`tag.sessions`). There is no owner field: ownership is `goal.owner`, and `LearningSession.objects.owned_by(user)` (filtering `goal__owner`) is the one way to look sessions up. Tags are a shared vocabulary, so reach a user's tags through their sessions (`Tag.objects.filter(sessions__in=LearningSession.objects.owned_by(user))`), never through an unscoped `tag.sessions`. Sessions are ordered newest first (`-date`, `-created_at`, `-id`). The admin lists goal, date and duration, filters by date and picks goal and tags with autocomplete. `with_tags()` prefetches tags in one query, alphabetical regardless of case (`Tag`'s own ordering is case-sensitive); use it wherever sessions are listed with their tags. Two aggregates, each one query, chained after `owned_by(user)`: `minutes_per_tag()` returns `[(tag name, minutes)]`, largest first with ties by name regardless of case, then `(None, minutes)` for untagged time if any (a LEFT JOIN on the tags, so a multi-tag session counts under each tag); `minutes_per_week(today, weeks)` returns `[(Monday, minutes)]` for exactly `weeks` Monday-start weeks ending with the one containing `today`, newest first, 0 for an empty week, sessions outside that range not counted (`TruncWeek` + `Sum`). Both return minutes, never hours; a grouping helper must end with its own `order_by(...)` or clear the incoming one with `.order_by()` (pinned by tests that pass an ordered queryset). Pages (`learning_sessions/urls.py`, namespace `learning_sessions`, mounted at the root) use shallow nesting: the routes that need the goal sit under it, `/goals/<goal_pk>/sessions/` (`list`, 20 per page, `{% querystring %}` links) and `/goals/<goal_pk>/sessions/new/` (`create`); the ones for one session take only its pk, `/sessions/<pk>/edit/` (`edit`) and `/sessions/<pk>/delete/` (`delete`, POST deletes). There is no session detail page: create, edit and delete redirect to the goal's page (no `next`). Two mixins in `learning_sessions/views.py` scope every view, with the same rules as `OwnGoalsMixin` (list first in the bases, never set `model`): `OwnSessionsMixin` (`get_queryset()` is `owned_by(request.user)`, so another user's session is a 404 like a missing one) and, for the goal routes, `GoalSessionsMixin`, which looks the goal up through `Goal.objects.owned_by` in `dispatch` right after the login check, before any form handling, so a POST to another user's goal is a plain 404, never a page of form errors. `SessionViewsScopingTests` walks the session routes (found through the root URLconf) and enforces both mixins; a new route must be added to it deliberately. `LearningSessionForm` has an explicit allow-list (`date`, `duration_minutes`, `notes`, plus a `TagListField` for `tags`); the goal comes from the URL (create passes `instance=LearningSession(goal=...)`) and can't be changed on edit. The date is an `<input type="date">` with an ISO format (a localised value would leave the browser's date input empty on edit); its default is the model's `timezone.localdate`, evaluated per request. The `duration` filter (`{% load session_format %}`) shows minutes as "45 min", "2 h" or "1 h 30 min" ("0 min" for none). `templates/learning_sessions/_session_item.html` renders one session for the list and the goal page.
- Resources: `resources.Resource` (app `resources`) is reference material for one goal. `goal` is a required foreign key (`goal.resources`, deleted with the goal and so with its user); there is no owner field: ownership is `goal.owner`, and `Resource.objects.owned_by(user)` (filtering `goal__owner`) is the one way to look resources up. `url` is an `HttpURLField` (a `URLField` subclass in `resources/models.py`) of up to 2,048 characters that accepts only `http`/`https`: resources are rendered as links, so `javascript:`, `data:` or `ftp:` must never get in. It *replaces* `URLField`'s default validator (which also allows ftp/ftps) instead of adding to it, so a bad URL gets one error, not two. `title` is required, up to 200 characters; `save()` and `clean_fields()` trim both `title` and `url`. `type` is `Resource.Type`, a `TextChoices` with `article`, `video`, `repo` and `doc`, defaulting to `article`. Three database constraints back the validators, because `update()`/`bulk_create()` skip them: a `CheckConstraint` on the URL scheme (`istartswith` `http://` or `https://`), a `CheckConstraint` on the type values (hard-coded; a test runs every `Type.values` entry through `update()` to keep them in step) and a `UniqueConstraint` on `(goal, url)` ("This goal already has this resource.", compared exactly as stored after trimming; the same URL on another goal is fine). `full_clean()` reports the unique one under `NON_FIELD_ERRORS`, but skips it when `goal` is excluded, which a ModelForm without a `goal` field does, so a form must check it itself: `ResourceForm` overrides `validate_constraints()` (where Django 6.1 checks a `UniqueConstraint`, not `validate_unique()`) to keep `goal` in, so a duplicate is the model's own non-field error. Resources are ordered newest first (`-created_at`, `-id`). `grouped_by_type()` evaluates a queryset once and returns `[(heading, [resources])]` in `Resource.Type` order ("Articles", "Videos", "Repos", "Docs", from `TYPE_HEADINGS`), leaving out empty types; a new type needs a heading there (a test covers every type). The admin lists title, type and goal, filters by type, searches title and URL, and picks the goal with autocomplete. Pages (`resources/urls.py`, namespace `resources`, mounted at the root) use the sessions' shallow nesting: `/goals/<goal_pk>/resources/new/` (`create`) and `/resources/<pk>/delete/` (`delete`, POST deletes); there is no resource page, list or edit, and both redirect to the goal's page (no `next`) with "Resource added." / "Resource deleted.". Two mixins in `resources/views.py` scope them, with the same rules as `OwnGoalsMixin` (list first in the bases, never set `model`): `OwnResourcesMixin` (`get_queryset()` is `owned_by(request.user)`) and `GoalResourcesMixin`, which looks the goal up through `Goal.objects.owned_by` in `dispatch` right after the login check, so a POST to another user's goal is a plain 404. `ResourceViewsScopingTests` walks the resource routes and enforces both; a new route must be added to it deliberately. `ResourceForm` has an explicit allow-list (`url`, `title`, `type`); the goal comes from the URL (`instance=Resource(goal=...)`). Its URL field is Django's default `forms.URLField`, so a scheme-less `example.com` is stored as `https://example.com` (pinned by a test) and the model's validator still limits schemes to http/https. `ResourceCreateView.form_valid` saves in a savepoint and, on `IntegrityError`, asks the model's `validate_constraints()` whether it was a duplicate (two identical attaches racing): if so it shows the same form error, otherwise it re-raises. GET and invalid POSTs to `create` render `resources/resource_form.html`; the goal page's Resources section lists `grouped_by_type()` (one query, through `owned_by`) with each title linking to its URL in a new tab (`rel="noopener noreferrer"`) and a Delete link, then the inline attach form (an unbound `ResourceForm`). The goal delete confirmation also says how many resources are deleted with the goal.
- Dashboard: the model-free app `dashboard` serves `/dashboard/` (`dashboard:index`, `DashboardView(LoginRequiredMixin, TemplateView)`, GET/HEAD only, template `dashboard/dashboard.html`), where log-in and sign-up land; the nav's first logged-in link. Its "Goals by status" section (`aria-labelledby="goals-by-status-heading"`) is a table: one row per status from `Goal.objects.owned_by(request.user).status_counts()` (context `status_rows`, `(value, label, count)` in `Goal.Status` order), each label linking to `goals:list?status=<value>`, and a Total row (`total_goals`, summed from the counts, no second query) linking to `goals:list`. With no goals a "Create your first goal" link to `goals:create` follows the table. Below it, "Hours per tag" (`hours-per-tag-heading`) lists `LearningSession.objects.owned_by(request.user).minutes_per_tag()` (context `tag_rows`): a Tag / Time table, the `None` row shown as "Untagged" and a note that a session with several tags counts under each (so no Total row), or "No sessions logged yet." without sessions. "Hours per week" (`hours-per-week-heading`) lists `minutes_per_week(timezone.localdate(), weeks=WEEKS_SHOWN)` (`week_rows`, `WEEKS_SHOWN = 8` in `dashboard/views.py`): "Week of <Monday as M j, Y>" rows, newest first, empty weeks at "0 min". Times use the `duration` filter; each per-tag and per-week Time cell also has a decorative `<progress aria-hidden="true">` (no text inside it, so row texts stay exact) scaled to `tag_max`/`week_max`, the table's largest value or 1, computed in the view from the rows already fetched. Every table sits in an `overflow-x-auto` wrapper. The page takes 5 queries (session, user, status counts, per-tag totals, per-week totals), pinned by `assertNumQueries` and by a few-vs-many comparison over goals, sessions and tags; page tests fix "today" by patching `django.utils.timezone.now`. The page title is set through `base.html`'s `{% block title %}` (default "Learning Companion"; the dashboard's is "Dashboard · Learning Companion").
- Django's built-in test runner (`django.test`), ruff for lint and formatting. Ruff's defaults include RUF012, so class-level options (`Meta.ordering`, `Meta.constraints`, admin `inlines`) are tuples. A test of a data migration must be a `TransactionTestCase` (see `profiles/tests/test_migrations.py`).
- Settings from the environment via `django-environ` (`src/config/env.py`). `SECRET_KEY` and `OPENAI_API_KEY` are required (both read raw through `required_raw()`, so a leading `$` isn't expanded, and a missing or blank one is an `ImproperlyConfigured` that names the variable, never the value), `DEBUG` defaults to `False`, `ALLOWED_HOSTS` to `localhost,127.0.0.1` and `OPENAI_MODEL` to `gpt-4.1-mini` (blank also means the default). `ALLOWED_HOSTS` and the optional `CSRF_TRUSTED_ORIGINS` (empty by default) share `trimmed_list()`; a trusted origin without `http://`/`https://` is a fixed-message `ImproperlyConfigured`. The optional `DATABASE_URL` is parsed by `database_config()` into `EnvSettings.database`, which is `None` when unset or blank, and `settings.py` then keeps its own `src/db.sqlite3` dict. django-environ only warns about a value it can't parse, accepts an unknown scheme as an engine, and raises a `ValueError` quoting part of the URL for a port it can't read (as with a password holding an unencoded `/`). So that `ValueError` is dropped, and any engine outside `Env.DB_SCHEMES` is a fixed-message `ImproperlyConfigured` raised `from None`, which never echoes the URL (it can hold a password). A new optional variable goes into `PATCHED_ENVIRON` in `test_settings.py` with a non-default value, so a developer's `.env` can't leak in. The process environment beats `.env`, and `.env.example` documents every variable (`test_env_example.py` keeps the list; the key's placeholder is `sk-dummy`). The tests never call the API, so a dummy `OPENAI_API_KEY` is enough for the suite and the dev server; `config/tests/test_env.py` builds environments through `environ()`, which supplies one.
- Container (`Dockerfile`, `.dockerignore`, `docker/entrypoint.sh`): two stages on `python:3.14-slim`.
  - `build` installs `requirements.txt` into `/opt/venv`, then runs `tailwind build` (it downloads the Linux binary from GitHub, so the build needs network) and `collectstatic`, with build-only dummy keys `export`ed inside that one `RUN`.
  - The final stage copies the virtualenv, `src/` (`.dockerignore` keeps out `.env`, local databases, the built CSS, the macOS binary, `work/` and `.claude/`) and the collected `src/staticfiles`.
  - It runs as the non-root `app` user (uid 10001) with `DATABASE_URL=sqlite:////app/data/db.sqlite3` on `VOLUME /app/data` and `EXPOSE 8000`.
  - Its `HEALTHCHECK` requests `http://127.0.0.1:8000/favicon.ico` through Python's `urllib` (slim has no curl), so a custom `ALLOWED_HOSTS` must keep `127.0.0.1`. Its `--start-interval` needs Docker Engine 25 or newer.
  - `.env.example` has `DATABASE_URL` only as a commented-out example (`test_env_example.py`'s `COMMENTED_EXAMPLES`): a blank line passed with `--env-file` would override the image's value. The documented run command adds `-e DEBUG=False`, because the example sets `DEBUG=True` and `-e` beats `--env-file`. It publishes on `127.0.0.1` only. The smoke script runs a container that way too.
  - The exec-form `ENTRYPOINT` runs `migrate --noinput` and then `exec "$@"`, so gunicorn is PID 1, and a missing key fails `migrate` with the variable named. `CMD` is gunicorn on `config.wsgi:application`, `0.0.0.0:8000`, with `--timeout 90` (above the AI calls' 30 s timeouts), `--no-control-socket` and `--worker-tmp-dir /dev/shm`; workers follow `WEB_CONCURRENCY`.
  - No key is ever an `ENV` or `ARG`. `config/tests/test_docker.py` parses the stages and pins all of this, plus the requirement pins, `.dockerignore` and the smoke script's presence.
  - `scripts/docker-smoke.sh` builds and runs the image (unique names, a random port, everything removed on exit) and checks it end to end; CI's `docker-smoke` job and the ticket review run it. It is not part of the suite, which needs no Docker.
  - Static files: WhiteNoise (`whitenoise.middleware.WhiteNoiseMiddleware` right after `SecurityMiddleware`) serves `STATIC_ROOT = BASE_DIR / "staticfiles"` (git-ignored). `STORAGES["staticfiles"]` is `CompressedStaticFilesStorage`, which gzips at `collectstatic` but keeps plain names: a manifest storage would change every `{% static %}` URL that tests pin and need `collectstatic` before any page renders.
  - Locally and in tests `STATIC_ROOT` doesn't exist, so `settings.py` filters WhiteNoise's "No directory at: " `UserWarning` by its message; a `module=` filter would match the calling handler, not WhiteNoise. `config/tests/test_static_files.py` collects into a temp dir to check gzip serving, and checks that the warning stays silent.
- CI: GitHub Actions, `.github/workflows/ci.yml` (workflow `CI`), on every `push` and `pull_request`, with `permissions: contents: read` and a `concurrency` group per workflow and ref that cancels an older run. Two jobs run in parallel; their ids, with no `name:` key, are the status check names that branch protection requires, so renaming one means updating `scripts/branch-protection.sh` and re-applying it.
  - `quality` (`ubuntu-latest`, Python 3.14 through `actions/setup-python@v7` with a pip cache on `requirements*.txt`) installs `requirements-dev.txt` and runs `ruff check .`, `ruff format --check .`, `manage.py check`, `manage.py makemigrations --check --dry-run` and `manage.py test src`, each its own named step. `SECRET_KEY` and `OPENAI_API_KEY` are dummies in the job's `env` (the tests never call the API); the workflow never references `secrets.`, and no `.env` is created.
  - `docker-smoke` runs `scripts/docker-smoke.sh`.
  - Both have a `timeout-minutes`, and every action is pinned to a major (`@v7`, Node 24; v4/v5 ran on the deprecated Node 20). `config/tests/test_ci.py` reads the workflow as text (no YAML parser in the requirements) and pins all of this, plus `REQUIRE_CHECKS="true"`, the README badge and the protection script's desired state.
  - Branch protection (`scripts/branch-protection.sh`; `desired <branch>` prints the body `apply` sends, offline): `main` and `develop` both require `quality` and `docker-smoke` from GitHub Actions (app 15368, not strict), with no force pushes or deletion. `main` keeps its PR requirement (0 approvals) with admins bound. `develop` has no PR requirement and admins are not bound, so the owner's `release` run can push its main-into-develop merge commit (an admin bypass of the required checks). Applying it is outward-facing: only after the user confirms.
- OpenAI Chat Completions for the AI features, through the `ai` app (SDK `openai` 3.x, which is built on `httpx2`). `ai.services.complete(system, user)` sends one request (`settings.OPENAI_MODEL`, the system prompt then the user's message) and returns the reply text, trimmed. `complete_json(system, user, *, name, schema)` sends the same request with `response_format` set to a strict `json_schema` (OpenAI Structured Outputs; a plain dict, as `create()` takes no pydantic classes) and returns the parsed JSON object; a reply that isn't a JSON object (invalid or truncated JSON, a list, a string) is `AIServiceError("The AI service returned an unexpected reply.")`, logged without the reply text. Both share one private request helper, so they have the same error rules. Keep `minItems`/`maxItems` out of schemas: strict mode's support for them is unconfirmed and an unsupported keyword would fail every request, so callers check counts themselves (as `parse_next_steps()` does). Callers handle only `ai.services.AIServiceError`: every SDK error (`openai.OpenAIError`) and an empty reply (including a refusal, which has no content) become one, with a message safe to show users and the SDK error chained as `__cause__`. Failures are logged at error level on `ai.services` by error type only, never the SDK's text or a traceback, because the SDK's authentication error echoes part of the key. `get_client(max_retries=MAX_RETRIES)` is the only place an `openai.OpenAI` is built (the key from settings, `TIMEOUT_SECONDS = 30`, `MAX_RETRIES = 2`; the SDK's own read timeout would be 600 s). The 30 s apply per network phase (connect, write, each read), not per call, and between retries the SDK honours a server's `Retry-After` of up to 120 s, so a call a user waits on from a page passes `max_retries=0`, as the goal summary and next steps do; other callers keep the default of 2. Every caller must catch `AIServiceError` and show its message: an uncaught one would put the chained SDK error, which can echo part of the key, into a 500 page or error log. No test may reach the network: service tests extend `ai/tests/test_services.py`'s `NoNetworkTestCase`, which fails any real client construction, and replace `get_client` with a fake. Never hardcode a key.

Decisions above that aren't implemented yet are delivered by the tickets on the board; keep this file in step as they land.

## Layout

- `src/manage.py`, `src/config/`: Django project (settings, root URLs, ASGI/WSGI)
- `src/<app>/`: one Django app per domain area, tests in `src/<app>/tests/` (`test_*.py`)
- `src/core/`: the home page, the `/favicon.ico` view and other site-wide pieces, and `forms.py` (`StyledFormMixin`, `StyledBoundField`: how every non-admin form renders). `src/core/tests/html.py` holds `PageParser`, the HTML helper shared by the apps' page tests, and `src/core/tests/pages.py` the every-page fixture for site-wide checks.
- `src/accounts/`: the custom user model, and sign-up, log-in and log-out under `/accounts/` (URL namespace `accounts`)
- `src/tags/`: the shared `Tag` model, plus its admin with a name search, which backs tag autocomplete, and `forms.py` (`TagListField`, `tags_as_text`), the typed-tags form field
- `src/profiles/`: `Profile` (one per user), the signal that creates it, the backfill migration, the admin inline, and the profile pages under `/profile/` (views, URLs, `ProfileForm`)
- `src/goals/`: the `Goal` model (status choices, ownership, `owned_by` queryset, `get_absolute_url`, admin), and the goal pages under `/goals/`: list, create, detail, edit, delete and the AI summary and next-steps actions (views, URLs, `GoalForm`, `prompts.py` for the AI features' prompts, the next-steps schema and its parsing)
- `src/learning_sessions/`: the `LearningSession` model (goal, date, duration in minutes, notes, tags; `owned_by` and `with_tags` queryset, duration `CheckConstraint`, admin), and the session pages: list and create under `/goals/<goal_pk>/sessions/`, edit and delete under `/sessions/<pk>/` (views, URLs, `LearningSessionForm`, the `duration` template filter in `templatetags/session_format.py`)
- `src/resources/`: the `Resource` model (goal, URL, title, type; `HttpURLField`, `owned_by` and `grouped_by_type` queryset, the URL-scheme, type and goal/URL constraints, admin), and the resource pages: attach under `/goals/<goal_pk>/resources/new/`, delete under `/resources/<pk>/delete/` (views, URLs, `ResourceForm`)
- `src/dashboard/`: the dashboard page at `/dashboard/` (views, URLs; no models), the landing page after log-in: goal counts per status, session time per tag and per week
- `src/ai/`: the OpenAI Chat Completions service (`services.py`: `complete`, `complete_json`, `AIServiceError`, `get_client`); no models, views or URLs (the summary and next-steps features build on it)
- `src/templates/`: project-wide templates (`base.html` layout, pages that extend it, `accounts/`, `profiles/`, `goals/`, `learning_sessions/`, `resources/` and `dashboard/` pages, `forms/` for the project form rendering, `components/` for shared pieces)
- `src/tailwind/`: the Tailwind source stylesheet (`source.css`, with the themes) and the vendored daisyUI plugin files
- `src/assets/`: static source directory (`STATICFILES_DIRS`): the favicons; the built `css/tailwind.css` is git-ignored
- `work/<ticket-id>/`: workflow artifacts per ticket (`ticket.md`, `plan.md`, `review.md`, `activity.log`)
- `work/backlog.md`: git-ignored local mirror of the GitHub project board
- `Dockerfile`, `.dockerignore`, `docker/entrypoint.sh`: the production image and its start-up
- `scripts/`: `docker-smoke.sh`, the image's end-to-end check, and `branch-protection.sh`, the GitHub branch protection of `main` and `develop`
- `.github/workflows/ci.yml`: the CI workflow (jobs `quality` and `docker-smoke`)
- `.claude/`: workflow rules, skills, hooks, the board sync script
- `instructions/`: the project handouts (requirements per feature)

## Workflow

Every change goes through the pipeline in `.claude/rules/workflow.md`: `refine-ticket` → `plan-ticket` → `tdd-implement` → `final-review` → `release`, driven one step per call by `factory-manager` (e.g. `/loop /factory-manager`). TDD rules: `.claude/rules/tdd.md`. Gitflow and commit conventions: `.claude/rules/git.md`.

- Tickets are GitHub issues on the project board (repo and board number in `.claude/hooks/config.sh`).
- Ticket branches `feature/<id>` / `fix/<id>` are cut from `develop` and squash-merged back into it; the branches are kept.
- After every ticket, `factory-manager` runs the `release` skill: `main` is merged into `develop` with a merge commit (conflicts are resolved there), then a PR from `develop` is merged into `main` with a merge commit. `main` only changes this way.
- The next ticket starts only once `main` has the previous one; a hook blocks new ticket branches while `develop` is ahead of `main`.
- A release that can't finish (red suite, failed checks, a conflict, unreviewed commits on `develop`) sets `release_status: blocked` in `.claude/state/workflow.json` and returns to `idle`; then only a `type:fix` ticket can start, and its release clears the flag. A human can also fix an outside cause and run `/release`.
- `REQUIRE_CHECKS` in `.claude/hooks/config.sh` is `"true"` (kept so by `test_ci.py`): a release PR merges only once both CI checks have passed, and the hook also re-runs the local suite + lint before `gh pr merge`. Ticket PRs aren't gated by the hook, but `develop`'s branch protection requires the checks and `factory-manager` waits for them.
- `factory-manager` and `release` read `gh pr checks` by exit code: `0` passed; `8` pending (wait); `1` with "no checks reported" means the run hasn't registered yet (`factory-manager` waits; `release` blocks under `REQUIRE_CHECKS`); `1` with a failed check stops and reports it.
- A paused ticket (approval recorded in its `ticket.md`) resumes on its existing branch: `refine-ticket` merges the latest `develop` into it and continues at `plan-ticket`.
- Source under `src/` is write-protected outside the `implementing` phase; hooks also gate commits, pushes and merges.

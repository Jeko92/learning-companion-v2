# Learning Companion

A learning companion for tracking goals and learning sessions, attaching resources, and getting AI-powered summaries and next steps. Built with Django through an AI-factory pipeline (Recap Project 6, handouts in `instructions/`).

## Stack

- Python 3.14, Django 6.1, SQLite (dev, tests and container)
- Server-rendered Django templates, Tailwind via `django-tailwind-cli` (standalone binary, no Node). The Tailwind version is pinned in `settings.py` (`TAILWIND_CLI_VERSION`), and the built CSS is git-ignored, so run `tailwind build` after checkout. Tests don't need the build.
- Auth: Django's built-in auth with the custom user model `accounts.User` (`AUTH_USER_MODEL = "accounts.User"`, an `AbstractUser` with no extra fields). Always refer to it through `get_user_model()` or `settings.AUTH_USER_MODEL`, never `django.contrib.auth.models.User`. Profile data goes on `profiles.Profile`, not on `User`. Every user saved through `save()` gets exactly one profile (`user.profile`: `name`, `cohort`, `focus_areas`). A `post_save` signal in `profiles/signals.py` creates it, and the data migration `profiles/0002` backfilled users who already existed. `bulk_create` and raw fixture loads skip the signal, so views must use `Profile.objects.get_or_create(user=request.user)`, not a bare `user.profile`. The User admin (`accounts/admin.py`) shows it as an inline on the change page only, never on the add page. Users view and edit their own profile at login-required pages: `/profile/` (`profiles:mine`) redirects to `/profile/<pk>/` (`profiles:detail`), and `/profile/<pk>/edit/` (`profiles:edit`) takes focus areas as comma-separated text. Any view that takes a pk must scope its queryset to `request.user`, as `profiles.views.OwnProfileMixin` does for profiles, so another user's pk is a 404, exactly like a missing one. A profile takes at most 20 focus areas (1,000 characters of input), checked before any tag lookup. Sign-up (`/accounts/signup/`), log-in (`/accounts/login/`) and log-out (`/accounts/logout/`, POST only) are `accounts` views, the last two thin subclasses of Django's `LoginView` and `LogoutView`. `LOGIN_URL = "accounts:login"`, `LOGIN_REDIRECT_URL = "/"` and `LOGOUT_REDIRECT_URL = "/"`. A `next` parameter is followed only for same-site URLs (Django's `url_has_allowed_host_and_scheme`); keep it that way for any new redirect.
- Tags: one shared `tags.Tag` vocabulary, used for a profile's `focus_areas` and for a learning session's `tags`. Names are normalised (NFKC, trimmed, inner whitespace collapsed), must not contain control or invisible characters (Unicode Cc/Cf) or commas (the separator for typed tag lists), and are unique regardless of case, through a database constraint on `Lower("name")`; on SQLite the case folding is ASCII-only. `Tag.objects.clean_name()` validates a name without touching the database (forms use it to reject bad entries before anything is saved). `save()` normalises the name; the 50-character limit and the character checks apply only through `full_clean()`/`clean_name()`; `update()` and `bulk_create()` bypass all of it. Rows written before the normalisation existed (or through those bypasses) aren't renormalised: there is no data migration, as there is no production data yet. So always turn typed input into tags with `Tag.objects.get_or_create_by_name()`, never `Tag.objects.create()`. It is the only creation path for typed names: it validates before its lookup (an over-long name is a `ValidationError`, never a database error), and it is safe when two requests create the same name at once. Forms take typed tags through `tags.forms.TagListField` (comma-separated text, so a form never lists other users' tags): it cleans to a list of names, NFKC-splits on commas, validates each entry with `clean_name()` (every bad entry named in the error), drops case-insensitive duplicates (the first spelling wins) and caps the input at 20 names and 1,000 characters (`max_tags`, and `noun` for the count message). It creates nothing; the form's `@transaction.atomic save()` and `_save_m2m()` turn the names into tags with `get_or_create_by_name()`, so a failure leaves neither the object nor new tags. `tags_as_text()` builds the field's initial value. `ProfileForm` (`noun="focus areas"`) and `LearningSessionForm` use it.
- Goals: `goals.Goal` is owned by one user (`owner`, `user.goals`, deleted with the user). Its fields are `title` (required, up to 200 characters, stored trimmed), optional `description`, `status` and `created_at`/`updated_at`. `Goal.Status` is a `TextChoices` with `planned`, `in-progress` and `done` (the hyphen matches the planned `?status=` filter); a database `CheckConstraint` enforces them, so `update()`/`bulk_create()` can't store anything else. Goals are ordered newest first (`-created_at`, then `-id`). Logged-in users list their goals at `/goals/` (`goals:list`, 20 per page) and create them at `/goals/new/` (`goals:create`). Each goal has a detail page `/goals/<pk>/` (`goals:detail`, which `Goal.get_absolute_url()` returns), an edit page `/goals/<pk>/edit/` and a delete confirmation `/goals/<pk>/delete/` (POST deletes). The detail page has a Sessions section: the 5 most recent sessions, the total time of all of them (one `Sum()` aggregate) and links to add a session and to the full list; the delete confirmation says how many sessions (and resources) are deleted with the goal. Both look sessions up through `LearningSession.objects.owned_by(request.user).filter(goal=...)`, and the detail page keeps a fixed query count (pinned by `assertNumQueries`; the Resources section adds one query, see Resources). Create and edit redirect to the goal through `get_absolute_url`. Every goal view looks goals up through `Goal.objects.owned_by(user)` via `goals.views.OwnGoalsMixin`, so another user's goal is a 404 identical to a missing one. **List `OwnGoalsMixin` first in a view's bases and never set `model` on a goal view**: listed later, Django's own `get_queryset()` wins, which raises `ImproperlyConfigured` without a model but would serve every user's goals with one. `GoalViewsScopingTests` walks `goals.urls` and enforces both rules for every goal lookup view (a new route must be added to it deliberately). The list filters by `?status=<planned|in-progress|done>` (unknown values show all); its pagination links use Django's `{% querystring %}` tag, so they keep the filter and escape anything else in the query. `GoalForm` has an explicit field allow-list (never `owner`); the owner is set from `request.user` in `form_valid`. The description is capped at 2,000 characters by a model-level `MaxLengthValidator`, so forms, `full_clean()` and the admin share one limit.
- Learning sessions: `learning_sessions.LearningSession` (app `learning_sessions`, because the label `sessions` belongs to `django.contrib.sessions`) records time spent on one goal. `goal` is a required foreign key (`goal.sessions`, deleted with the goal and so with its user). `date` defaults to today (`timezone.localdate`), and the `reject_future_dates` validator rejects a future date. That runs only through `full_clean()`, with no database constraint because "today" moves. The initial migration refers to the validator by its dotted path, so renaming it needs a migration. `duration_minutes` is whole minutes, 1 to 1,440, enforced by validators and by a `CheckConstraint` (`PositiveIntegerField` alone would allow 0); hour totals divide `Sum()` by 60. `notes` is optional and capped at 2,000 characters by a `MaxLengthValidator`, and `tags` is a many-to-many to `tags.Tag` (`tag.sessions`). There is no owner field: ownership is `goal.owner`, and `LearningSession.objects.owned_by(user)` (filtering `goal__owner`) is the one way to look sessions up. Tags are a shared vocabulary, so reach a user's tags through their sessions (`Tag.objects.filter(sessions__in=LearningSession.objects.owned_by(user))`), never through an unscoped `tag.sessions`. Sessions are ordered newest first (`-date`, `-created_at`, `-id`). The admin lists goal, date and duration, filters by date and picks goal and tags with autocomplete. `with_tags()` prefetches tags in one query, alphabetical regardless of case (`Tag`'s own ordering is case-sensitive); use it wherever sessions are listed with their tags. Pages (`learning_sessions/urls.py`, namespace `learning_sessions`, mounted at the root) use shallow nesting: the routes that need the goal sit under it, `/goals/<goal_pk>/sessions/` (`list`, 20 per page, `{% querystring %}` links) and `/goals/<goal_pk>/sessions/new/` (`create`); the ones for one session take only its pk, `/sessions/<pk>/edit/` (`edit`) and `/sessions/<pk>/delete/` (`delete`, POST deletes). There is no session detail page: create, edit and delete redirect to the goal's page (no `next`). Two mixins in `learning_sessions/views.py` scope every view, with the same rules as `OwnGoalsMixin` (list first in the bases, never set `model`): `OwnSessionsMixin` (`get_queryset()` is `owned_by(request.user)`, so another user's session is a 404 like a missing one) and, for the goal routes, `GoalSessionsMixin`, which looks the goal up through `Goal.objects.owned_by` in `dispatch` right after the login check, before any form handling, so a POST to another user's goal is a plain 404, never a page of form errors. `SessionViewsScopingTests` walks the session routes (found through the root URLconf) and enforces both mixins; a new route must be added to it deliberately. `LearningSessionForm` has an explicit allow-list (`date`, `duration_minutes`, `notes`, plus a `TagListField` for `tags`); the goal comes from the URL (create passes `instance=LearningSession(goal=...)`) and can't be changed on edit. The date is an `<input type="date">` with an ISO format (a localised value would leave the browser's date input empty on edit); its default is the model's `timezone.localdate`, evaluated per request. The `duration` filter (`{% load session_format %}`) shows minutes as "45 min", "2 h" or "1 h 30 min" ("0 min" for none). `templates/learning_sessions/_session_item.html` renders one session for the list and the goal page.
- Resources: `resources.Resource` (app `resources`) is reference material for one goal. `goal` is a required foreign key (`goal.resources`, deleted with the goal and so with its user); there is no owner field: ownership is `goal.owner`, and `Resource.objects.owned_by(user)` (filtering `goal__owner`) is the one way to look resources up. `url` is an `HttpURLField` (a `URLField` subclass in `resources/models.py`) of up to 2,048 characters that accepts only `http`/`https`: resources are rendered as links, so `javascript:`, `data:` or `ftp:` must never get in. It *replaces* `URLField`'s default validator (which also allows ftp/ftps) instead of adding to it, so a bad URL gets one error, not two. `title` is required, up to 200 characters; `save()` and `clean_fields()` trim both `title` and `url`. `type` is `Resource.Type`, a `TextChoices` with `article`, `video`, `repo` and `doc`, defaulting to `article`. Three database constraints back the validators, because `update()`/`bulk_create()` skip them: a `CheckConstraint` on the URL scheme (`istartswith` `http://` or `https://`), a `CheckConstraint` on the type values (hard-coded; a test runs every `Type.values` entry through `update()` to keep them in step) and a `UniqueConstraint` on `(goal, url)` ("This goal already has this resource.", compared exactly as stored after trimming; the same URL on another goal is fine). `full_clean()` reports the unique one under `NON_FIELD_ERRORS`, but skips it when `goal` is excluded, which a ModelForm without a `goal` field does, so a form must check it itself: `ResourceForm` overrides `validate_constraints()` (where Django 6.1 checks a `UniqueConstraint`, not `validate_unique()`) to keep `goal` in, so a duplicate is the model's own non-field error. Resources are ordered newest first (`-created_at`, `-id`). `grouped_by_type()` evaluates a queryset once and returns `[(heading, [resources])]` in `Resource.Type` order ("Articles", "Videos", "Repos", "Docs", from `TYPE_HEADINGS`), leaving out empty types; a new type needs a heading there (a test covers every type). The admin lists title, type and goal, filters by type, searches title and URL, and picks the goal with autocomplete. Pages (`resources/urls.py`, namespace `resources`, mounted at the root) use the sessions' shallow nesting: `/goals/<goal_pk>/resources/new/` (`create`) and `/resources/<pk>/delete/` (`delete`, POST deletes); there is no resource page, list or edit, and both redirect to the goal's page (no `next`) with "Resource added." / "Resource deleted.". Two mixins in `resources/views.py` scope them, with the same rules as `OwnGoalsMixin` (list first in the bases, never set `model`): `OwnResourcesMixin` (`get_queryset()` is `owned_by(request.user)`) and `GoalResourcesMixin`, which looks the goal up through `Goal.objects.owned_by` in `dispatch` right after the login check, so a POST to another user's goal is a plain 404. `ResourceViewsScopingTests` walks the resource routes and enforces both; a new route must be added to it deliberately. `ResourceForm` has an explicit allow-list (`url`, `title`, `type`); the goal comes from the URL (`instance=Resource(goal=...)`). Its URL field is Django's default `forms.URLField`, so a scheme-less `example.com` is stored as `https://example.com` (pinned by a test) and the model's validator still limits schemes to http/https. `ResourceCreateView.form_valid` saves in a savepoint and, on `IntegrityError`, asks the model's `validate_constraints()` whether it was a duplicate (two identical attaches racing): if so it shows the same form error, otherwise it re-raises. GET and invalid POSTs to `create` render `resources/resource_form.html`; the goal page's Resources section lists `grouped_by_type()` (one query, through `owned_by`) with each title linking to its URL in a new tab (`rel="noopener noreferrer"`) and a Delete link, then the inline attach form (an unbound `ResourceForm`). The goal delete confirmation also says how many resources are deleted with the goal.
- Django's built-in test runner (`django.test`), ruff for lint and formatting. Ruff's defaults include RUF012, so class-level options (`Meta.ordering`, `Meta.constraints`, admin `inlines`) are tuples. A test of a data migration must be a `TransactionTestCase` (see `profiles/tests/test_migrations.py`).
- Settings from the environment via `django-environ` (`src/config/env.py`). `SECRET_KEY` is required, `DEBUG` defaults to `False` and `ALLOWED_HOSTS` to `localhost,127.0.0.1`. The process environment beats `.env`, and `.env.example` documents every variable.
- OpenAI Chat Completions for the AI features; API key from `.env`, never hardcoded

Decisions above that aren't implemented yet are delivered by the tickets on the board; keep this file in step as they land.

## Commands

Run from the repo root.

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r requirements-dev.txt   # setup
cp .env.example .env   # then set SECRET_KEY; required by runserver and the test suite
./.venv/bin/python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"   # generate a SECRET_KEY
./.venv/bin/python src/manage.py tailwind build                              # build the CSS (required after checkout; downloads the pinned binary into src/.django_tailwind_cli/)
./.venv/bin/python src/manage.py tailwind runserver                          # dev server plus Tailwind watcher (everyday development)
./.venv/bin/python src/manage.py runserver                                   # dev server only
./.venv/bin/python src/manage.py test src                                    # full suite (what the hooks run)
./.venv/bin/python src/manage.py test <app>.tests.test_<x> --verbosity 2     # one test module
./.venv/bin/ruff check .                                                     # lint (what the hooks run)
./.venv/bin/ruff format .                                                    # format
./.venv/bin/python src/manage.py makemigrations && ./.venv/bin/python src/manage.py migrate
python3 .claude/scripts/board.py sync                                        # mirror the GitHub board into work/backlog.md
```

## Layout

- `src/manage.py`, `src/config/`: Django project (settings, root URLs, ASGI/WSGI)
- `src/<app>/`: one Django app per domain area, tests in `src/<app>/tests/` (`test_*.py`)
- `src/core/`: the home page and other site-wide views. `src/core/tests/html.py` holds `PageParser`, the HTML helper shared by the apps' page tests.
- `src/accounts/`: the custom user model, and sign-up, log-in and log-out under `/accounts/` (URL namespace `accounts`)
- `src/tags/`: the shared `Tag` model, plus its admin with a name search, which backs tag autocomplete, and `forms.py` (`TagListField`, `tags_as_text`), the typed-tags form field
- `src/profiles/`: `Profile` (one per user), the signal that creates it, the backfill migration, the admin inline, and the profile pages under `/profile/` (views, URLs, `ProfileForm`)
- `src/goals/`: the `Goal` model (status choices, ownership, `owned_by` queryset, `get_absolute_url`, admin), and the goal pages under `/goals/`: list, create, detail, edit and delete (views, URLs, `GoalForm`)
- `src/learning_sessions/`: the `LearningSession` model (goal, date, duration in minutes, notes, tags; `owned_by` and `with_tags` queryset, duration `CheckConstraint`, admin), and the session pages: list and create under `/goals/<goal_pk>/sessions/`, edit and delete under `/sessions/<pk>/` (views, URLs, `LearningSessionForm`, the `duration` template filter in `templatetags/session_format.py`)
- `src/resources/`: the `Resource` model (goal, URL, title, type; `HttpURLField`, `owned_by` and `grouped_by_type` queryset, the URL-scheme, type and goal/URL constraints, admin), and the resource pages: attach under `/goals/<goal_pk>/resources/new/`, delete under `/resources/<pk>/delete/` (views, URLs, `ResourceForm`)
- `src/templates/`: project-wide templates (`base.html` layout, pages that extend it, `accounts/`, `profiles/`, `goals/`, `learning_sessions/` and `resources/` pages)
- `src/assets/`: static source directory (`STATICFILES_DIRS`); the built `css/tailwind.css` is git-ignored
- `work/<ticket-id>/`: workflow artifacts per ticket (`ticket.md`, `plan.md`, `review.md`, `activity.log`)
- `work/backlog.md`: git-ignored local mirror of the GitHub project board
- `.claude/`: workflow rules, skills, hooks, the board sync script
- `instructions/`: the project handouts (requirements per feature)

## Workflow

Every change goes through the pipeline in `.claude/rules/workflow.md`: `refine-ticket` → `plan-ticket` → `tdd-implement` → `final-review` → `release`, driven one step per call by `factory-manager` (e.g. `/loop /factory-manager`). TDD rules: `.claude/rules/tdd.md`. Gitflow and commit conventions: `.claude/rules/git.md`.

- Tickets are GitHub issues on the project board (repo and board number in `.claude/hooks/config.sh`).
- Ticket branches `feature/<id>` / `fix/<id>` are cut from `develop` and squash-merged back into it; the branches are kept.
- After every ticket, `factory-manager` runs the `release` skill: `main` is merged into `develop` with a merge commit (conflicts are resolved there), then a PR from `develop` is merged into `main` with a merge commit. `main` only changes this way.
- The next ticket starts only once `main` has the previous one; a hook blocks new ticket branches while `develop` is ahead of `main`.
- A release that can't finish (red suite, failed checks, a conflict, unreviewed commits on `develop`) sets `release_status: blocked` in `.claude/state/workflow.json` and returns to `idle`; then only a `type:fix` ticket can start, and its release clears the flag. A human can also fix an outside cause and run `/release`.
- `REQUIRE_CHECKS` in `.claude/hooks/config.sh` is `"false"` until CI exists: release PRs without checks merge on the local suite + lint, which the hook re-runs before `gh pr merge`. Flip it to `"true"` with the `ci-tests` ticket.
- A paused ticket (approval recorded in its `ticket.md`) resumes on its existing branch: `refine-ticket` merges the latest `develop` into it and continues at `plan-ticket`.
- Source under `src/` is write-protected outside the `implementing` phase; hooks also gate commits, pushes and merges.
